# Сервис интеграции с Яндекс.Картами (GeoReviews)

Упрощённая модель сервиса для работы с отзывами и данными бизнеса на картах (Яндекс.Карты, 2ГИС). Проект выполнен в качестве тестового задания на позицию Fullstack-разработчика.

- **Бэкенд / API**: PHP 8.2+, Laravel 12 (REST API, Sanctum, Queues, SQLite / MySQL).
- **Фронтенд / SPA**: Vue 3 (Composition API, `<script setup>`), TypeScript (строгая типизация без `any`), Pinia, Vue Router 4, Tailwind CSS v4.

---

## 🎯 Реализованный функционал

1. **Экран авторизации (`/login`)**:
   - SPA-аутентификация через Laravel Sanctum (выпуск и валидация Bearer токенов).
   - Защита маршрутов через Navigation Guards во Vue Router.
   - Кнопка быстрого заполнения сид-пользователя в 1 клик.
   - Тестовый аккаунт: **`admin@georeviews.local`** / **`password`**.

2. **Экран настроек и подключения карточки (`/organizations`)**:
   - Валидация ссылок на Яндекс.Карты (поддерживаются полные ссылки со слагом, числовые ID, короткие ссылки).
   - Готовые кнопки-примеры для мгновенной проверки реальных организаций («Додо Пицца», «Шоколадница», «Вкусно — и точка»).
   - Асинхронное подключение и опрос статуса парсинга (Live Progress Bar с процентами).

3. **Экран данных организации (`/organizations/:id`)**:
   - **Средний рейтинг компании** (с детальной шкалой звёзд и числовым значением, например `4.9`).
   - **Точные числа**: отдельно количество оценок (`ratings_count`) и количество отзывов (`reviews_count`).
   - **Все отзывы по карточке** (парсинг до ~600 отзывов).
   - **Постраничная навигация по 50 отзывов на страницу** без перезагрузки экрана (SPA).
   - **Карточка каждого отзыва**: имя автора, аватар/инициалы, статус («Знаток города 8 уровня»), звёздная оценка, форматированная дата по стандарту ru-RU, полный текст отзыва, а также официальный ответ компании при наличии.
   - **Фильтрация и сортировка**: фильтр по количеству звёзд (1–5) и сортировка по дате / оценке.
    - **Вкладка «История изменений (Снимки)»**: визуализация снимков данных до/после каждого цикла синхронизации.
    - **Визуальный график динамики репутации**: чистый легковесный SVG-компонент тренда рейтинга и притока отзывов по снимкам синхронизации с интерактивными тултипами и подсчетом дельты рейтинга.
    - **Экспорт отзывов для бизнеса (CSV / Excel)**: потоковая выгрузка отзывов в CSV с заголовком UTF-8 BOM (`\xEF\xBB\xBF`) для бесшовного открытия в Microsoft Excel без проблем с кодировкой, с поддержкой фильтрации по рейтингу.

4. **Интерактивная панель администратора (`/admin`)**:
   - **Дашборд системных метрик**: статус пула прокси (готовые к работе, на охлаждении, средняя задержка в мс), объемы базы данных (число организаций, отзывов, снимков), мониторинг очередей задач и сбоев (`failed_jobs`), версия PHP и Laravel.
   - **Управление пулом ротации прокси в реальном времени**:
     - Интерактивная таблица с фильтрами по статусам (Все, Активные, Охлаждение, Отключенные) и поиском по IP/хосту.
     - Маскированные эндпоинты (`http://user:***@host:port`), фиксация ошибок и средней задержки.
     - Мгновенное включение / отключение прокси в 1 клик и удаление из пула.
     - Модальное окно пакетного добавления прокси-серверов в различных форматах (с поддержкой авторизации `ip:port:user:pass`, `ip:port@user:pass`, `user:pass@ip:port`).
   - **Безопасность и разграничение доступа**:
     - Маршрут `/admin` защищен Navigation Guard во Vue Router по флагу `is_admin`.
     - Ссылка в шапке приложения отображается только для авторизованных администраторов.

5. **Административный контур бэкенда и безопасность (`/api/admin/*`)**:
   - Двухуровневый контроль доступа (**Middleware `admin.access`**):
     - Либо сессия администратора с флагом `is_admin: true` через Laravel Sanctum (пользователь `admin@georeviews.local`).
     - Либо выделенный сервисный ключ `X-Admin-Key` / `X-API-Key` (защита от timing-атак через `hash_equals()`) для внешних скриптов и провайдеров.
   - Изолированное управление динамическим пулом прокси (`/api/admin/proxies`).
   - Системный мониторинг здоровья очередей, БД и задержек (`/api/admin/settings`).

6. **Комплексный Healthcheck & Readiness Probes (SRE / DevOps)**:
   - `/api/health`: быстрая liveness-проверка для балансировщиков нагрузки.
   - `/api/health/ready`: глубокая готовность сервиса к трафику с замером сетевой задержки к БД (`latency_ms`), мониторингом очередей, проверкой свободного места на диске и диагностикой доступности пула прокси.

7. **Санитизация контента и защита от Stored XSS**:
   - Выделенный сервис `App\Support\ContentSanitizer`, очищающий опасные HTML-теги, скрипты, SVG-векторы и управляющие символы в текстах отзывов, именах авторов и ответах компании.
   - Проверка безопасности URL-аватаров авторов (блокировка вредоносных протоколов `javascript:`, `data:`).

## 🏗 Архитектура и принципы проектирования

Проект строго следует **Dependency Inversion Principle (DIP)**:
```text
┌─────────────────────────────────────────────────────────┐
│                  Domain Layer (Контракты)               │
│  - YandexParserInterface                                │
│  - DTOs: ParsedOrganizationDto, ParsedReviewDto         │
│  - Exceptions: Captcha, MarkupChanged, NotFound         │
└────────────────────────────▲────────────────────────────┘
                             │ implements / depends on
┌────────────────────────────┴────────────────────────────┐
│              Infrastructure Layer (Реализация)          │
│  - YandexMapsParserService (HTTP-клиент, JSON-парсер)   │
│  - User-Agent rotation, backoff, Captcha-detection      │
└────────────────────────────▲────────────────────────────┘
                             │ injected into
┌────────────────────────────┴────────────────────────────┐
│               Application Layer & Services              │
│  - OrganizationSyncService (Идемпотентный upsert)       │
│  - SyncOrganizationReviewsJob (Фоновые очереди, retry)  │
└────────────────────────────▲────────────────────────────┘
                             │ consumed by
┌────────────────────────────┴────────────────────────────┐
│                    HTTP Presentation                    │
│  - AuthController, OrganizationController               │
│  - FormRequests (ConnectOrganizationRequest)            │
└─────────────────────────────────────────────────────────┘
```

- **Domain** не зависит от инфраструктуры или фреймворка.
- Замена парсера (например, на Puppeteer или сторонний API-шлюз) производится изменением одного биндинга в `AppServiceProvider`.
- Во фронтенде соблюдена строгая типизация TypeScript (флаг `noImplicitAny`, полное отсутствие типа `any`).

## 📋 Ответы на «Дополнительные требования»

### 1. Устойчивость к смене разметки

**Как парсер поймет, что он сломался?**
Яндекс регулярно обновляет клиентские бандлы и стили. Вместо хрупкого парсинга HTML-классов вида `.business-review-view__body` (которые обфусцируются или переименовываются в `.sc-1x9a8f`), парсер опирается на серверный блок состояния `<script type="application/json" class="state-view">`.

Детекция поломки реализована на трёх эшелонах:
1. **Эшелон структуры документа**: если тег `<script class="state-view">` не обнаружен или вернулся невалидный JSON, выбрасывается типизированное исключение `YandexMarkupChangedException`.
2. **Эшелон структуры данных**: проверяется наличие ключей `stack[0].results.items[0]` и `reviewResults`. Если поле исчезло или сменило тип (например, `ratingData.ratingValue` переехало), парсер не возвращает тихие нули, а фиксирует ошибку в лог с дампом структуры (`Log::error`) и сохраняет статус `failed` в `organizations.last_sync_error`.
3. **Эшелон аномалий (Sanity Checks)**: если организация найдена, но извлечено ровно 0 отзывов при общем счетчике `reviewCount > 0`, система фиксирует предупреждение о возможной смене формата выдачи.

---

### 2. Обоснование подхода к парсингу (JSON state-view vs Headless-браузер)

В данном решении выбран **разбор серверного JSON-состояния карточки (`state-view`) через HTTP-клиент с постраничной навигацией `?page=N`**.

| Критерий | Разбор JSON (`state-view`) | Headless-браузер (Puppeteer/Playwright) |
| :--- | :--- | :--- |
| **Скорость сбора** | **Высокая** (150–400 мс на 50 отзывов) | **Низкая** (3–8 сек на страницу с эмуляцией скролла) |
| **Потребление ресурсов** | **Минимальное** (3–5 МБ RAM на процесс PHP) | **Высокое** (150–400 МБ RAM на каждый процесс Chromium) |
| **Сложность инфраструктуры** | Стандартный PHP с cURL/Guzzle | Требуются Node.js, системные библиотеки Linux, Xvfb |
| **Точность данных** | Исходные немодифицированные типы (ID, float рейтинг) | Риск обрезки текста кнопкой «Читать полностью» |
| **Риск поломки** | Смена структуры JSON-состояния | Смена CSS-селекторов и таймингов бесконечного скролла |

**Итог:** Для продакшн-сервиса идеальна **гибридная модель**:
- **95% запросов** идут по «быстрому пути» через легковесный разбор внутреннего JSON `state-view` по HTTP (150–300 мс на страницу, 3–5 МБ RAM, отсутствие браузерных накладных расходов).
- **5% критических ситуаций** (попадание прокси под агрессивный поведенческий антифрод или сложную SmartCaptcha) делегируются **резервному Fallback-драйверу на базе Headless Chromium с прямым протоколом CDP (Chrome DevTools Protocol)**. В отличие от классического Selenium/WebDriver, прямое управление через CDP полностью исключает флаг `navigator.webdriver`, позволяет маскировать Canvas/WebGL фингерпринты, эмулировать естественные кривые движения мыши и перехватывать данные `state-view` прямо из сетевого контекста страницы.

### 3. Масштаб и фоновая обработка

При подключении сети из ~50 филиалов и объёме ~30 000 отзывов синхронный парсинг внутри HTTP-запроса недопустим из-за таймаутов (Nginx 60s) и пиковых нагрузок.

**Реализованная архитектура масштабирования:**
1. **Queue Jobs**: парсинг вынесен в фоновую задачу `SyncOrganizationReviewsJob`. Контроллер мгновенно возвращает ответ `201 Created` со статусом `pending`, а фронтенд отслеживает прогресс через короткий polling (или WebSocket/SSE).
2. **Chunking и постраничный сбор**: отзывы извлекаются пачками по 50 штук (до 12 страниц на организацию). После каждой страницы обновляется процент прогресса `sync_progress = round((page / totalPages) * 100)`.
3. **Отказоустойчивость (Retries & Backoff)**: в джобе настроены `$tries = 3` и экспоненциальная задержка `$backoff = [10, 30, 60]`. При кратковременном сетевом сбое задача не теряется, а повторяется через прогрессивный интервал.
4. **Масштабирование воркеров**: при росте сети достаточно поднять параллельные воркеры (`php artisan queue:work --queue=reviews --concurrency=5`), которые независимо разбирают очередь из Redis/RabbitMQ.

### 4. Анти-бан на объёме и динамическая ротация прокси

Для регулярного сбора данных без официального API и без необходимости перезапуска воркеров спроектирован **модуль динамической ротации прокси**:

1. **Динамический пул прокси в БД (`ProxyRotatorInterface` / `DatabaseProxyRotator`)**:
   - Прокси хранятся в таблице `proxy_servers` (поддержка `http`, `https`, `socks5` с авторизацией по логину/паролю).
   - Изменения (добавление, отключение, смена портов) применяются **мгновенно на лету без перезапуска приложения и очередей**.
   - Ротация по принципу **LRU (Least Recently Used)**: запросы равномерно распределяются между всеми активными серверами пула.
   - Если пул пуст (например, в локальной разработке) — прозрачный fallback на прямое подключение.
2. **Автоматический карантин (Cooldown при SmartCaptcha)**:
   - При обнаружении страницы капчи прокси не удаляется, а автоматически переводится в карантин на 30 минут (`cooldown_until = now()->addMinutes(30)`).
   - Задача повторяется через следующий чистый прокси из пула.
3. **Самовосстановление и мониторинг качества (Health Checks)**:
   - Сбор метрик по каждому прокси: число успехов (`success_count`), число ошибок (`fails_count`), скользящая средняя задержка (`avg_response_time_ms`), текст последней ошибки.
   - Временная заморозка на 15 минут при 5 ошибках подряд.
   - Окончательная деактивация (`is_active = false`) при 15 ошибках подряд.
4. **Управление пулом через CLI и REST API**:
   - **CLI-команды**:
     - `php artisan proxy:add http://user:pass@host:port` — добавление прокси в пул.
     - `php artisan proxy:list` — сводная таблица статусов, задержек и ошибок.
   - **REST API** (под защитой Sanctum):
     - `GET /api/proxies` — список прокси с детальными метриками.
     - `POST /api/proxies` — добавление одного или пачки прокси.
     - `POST /api/proxies/{id}/toggle` — мгновенная активация / деактивация.
     - `DELETE /api/proxies/{id}` — удаление из пула.
5. **Ротация цифровых отпечатков (Fingerprint & User-Agents)**:
   - Ротация реальных браузерных заголовков `User-Agent`, `Sec-Ch-Ua`, `Sec-Ch-Ua-Platform`, `Accept-Language`.
   - Интеллектуальный Jitter (случайная пауза 300–800 мс) между страницами.

---

### 5. Идемпотентность и история изменений

1. **Идемпотентность**:
   - В таблице `reviews` создан уникальный композитный индекс `unique(['organization_id', 'yandex_review_id'])`.
   - При повторном сборе выполняется метод `updateOrCreate`, который обновляет счетчики лайков/ответы организации и предотвращает дублирование.
2. **Модель снимков данных (`organization_snapshots`)**:
   - Каждая синхронизация создает запись в таблице `organization_snapshots`:
     - `rating_before` → `rating_after`
     - `ratings_count_before` → `ratings_count_after`
     - `reviews_count_before` → `reviews_count_after`
     - `new_reviews_added` (число впервые обнаруженных отзывов)
     - `updated_reviews_count` (число обновленных отзывов)
     - `snapshot_at` (метка времени)
   - Это позволяет строить графики динамики репутации («Как изменился рейтинг за прошлый месяц», «Сколько новых отзывов поступило за неделю»).
